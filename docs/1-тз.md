# ТЗ

## «Котик в мире арифметики» — обучающая игра-кроссворд


## 1. Общие положения

### 1.1. Назначение документа

Настоящее ТЗ определяет требования к обучающей игре «Котик в мире арифметики» для детей дошкольного и младшего школьного возраста. Документ является основанием для проектирования, разработки и приёмки продукта.

### 1.2. Целевая аудитория

Дети 5–9 лет. Игра должна быть понятна без чтения длинных инструкций, интерфейс — крупный, контрастный, интуитивный.

### 1.3. Канал распространения

RuStore. Приложение должно распространяться в виде Android-сборки, соответствующей правилам модерации RuStore.


## 2. Игровая механика

### 2.1. Кроссворд с арифметическими компонентами

Сетка кроссворда содержит клетки, часть из которых заполнена числами и знаками действий, а часть должна быть заполнена ребёнком. Каждое «слово» кроссворда — это арифметическое равенство с одним неизвестным компонентом.

**Базовый уровень (сложение и вычитание):** ребёнок находит первое слагаемое, второе слагаемое, сумму, уменьшаемое, вычитаемое, разность.

**Продвинутый уровень (умножение и деление):** ребёнок находит первый множитель, второй множитель, произведение, делимое, делитель, частное.

### 2.2. Режим на время

Каждый кроссворд решается на время. Таймер запускается при открытии кроссворда. По истечении времени кроссворд завершается, результат фиксируется в статистике.

### 2.3. Настройки сложности

Перед началом игры настраиваются:

- **Диапазон чисел:** до 10, до 20, до 30 и далее (конкретный перечень определяется на этапе контентного наполнения).
- **Операции:** сложение, вычитание, умножение, деление (комбинируются).
- **Отображение знаков:** выбор между `×` и `*`; между `÷` и `:`.


## 3. Маскот-котик

### 3.1. Роль и поведение

Котик в учительской шляпе постоянно присутствует на экране — сидит, лежит или стоит на полянке в углу. Его задачи:

- хвалить ребёнка после правильных решений;
- давать подсказки в текстовом или визуальном виде;
- мягко указывать на ошибку, объясняя, какой компонент действия стоит проверить.

### 3.2. Требования к реализации

Тексты реплик хранятся отдельно от кода (конфигурационные файлы), чтобы в будущем добавить голосовое сопровождение без переписывания логики. Котик не должен перекрывать игровое поле или элементы управления.


## 4. Статистика и прогресс

### 4.1. Локальное хранение (обязательно на первом этапе)

Статистика каждого решённого кроссворда сохраняется локально на устройстве: время решения, количество ошибок, сложность, задействованные операции. Хранилище — IndexedDB (переживает перезапуск приложения, работает без интернета).

### 4.2. Синхронизация (на будущее, архитектурно заложить)

Предусмотреть возможность выгрузки и синхронизации статистики через серверную часть. На первом релизе синхронизация не обязательна, но модель данных и API должны допускать её добавление без ломки существующей логики.


## 5. Пользователи, роли и группы (архитектурный задел)

### 5.1. Многоролевая модель

Система должна быть спроектирована с расчётом на несколько ролей. На первом этапе — минимум: `ребёнок` (игрок) и `родитель` (просмотр статистики). В дальнейшем возможно добавление роли `организатор группы` (учитель/родитель, создающий группу).

### 5.2. Группы и соревнования (на будущее)

Архитектурно заложить сущности:

- **Группа** — объединение пользователей (например, класс или семья).
- **Соревнование** — сравнение результатов участников группы по заданным правилам (время, точность, количество решённых кроссвордов).

На первом релизе группы и соревнования могут отсутствовать в UI, но схема данных и API должны допускать их добавление без переработки ядра.

### 5.3. Аутентификация

**Первый этап:** вход по любому email (без подтверждения или с минимальной проверкой — на усмотрение реализации). Это снижает порог входа для родителей, которые настраивают игру для ребёнка.

**Последующие этапы:** добавление OAuth-провайдеров — VK ID, MAX, Госуслуги (ЕСИА). Архитектура аутентификации должна быть провайдеро-независимой: единый внутренний `user_id`, к которому привязываются внешние идентификаторы.


## 6. Технические требования

### 6.1. Монорепозиторий

Фронтенд и бэкенд располагаются в одном монорепозитории. Рекомендуемая структура:

```
/apps
  /client      — фронтенд (PWA)
  /server      — бэкенд (Node.js)
/packages
  /shared      — общие типы, константы, конфигурация кроссвордов
  /config      — ESLint, TypeScript, Prettier
```

Инструмент управления монорепозиторием — на усмотрение команды (pnpm workspaces, Turborepo, Nx).

### 6.2. Фронтенд

**Стек:** React + TypeScript + Vite + `vite-plugin-pwa`.

**Требования:**

- Работа в браузере на компьютере и как установленное приложение на Android.
- Полноценный офлайн-режим: Service Worker кэширует оболочку и контент. При отсутствии интернета игра запускается и функционирует, за исключением функций, требующих сети (если таковые появятся).
- Адаптивная вёрстка под мобильные экраны и десктоп.
- Крупные интерактивные элементы, минимум текста, визуальные подсказки.

**Упаковка для RuStore:** TWA через Bubblewrap либо WebView-обёртка с локальным бандлом. Ключевое требование модерации RuStore: WebView-приложение не должно выглядеть как «сайт в рамке» — без адресной строки, меню браузера и настроек сайта; при отсутствии интернета должен отображаться корректный плейсхолдер, а не ошибка браузера . Приложение должно восприниматься как самостоятельный продукт.

### 6.3. Бэкенд

**Стек:** Node.js + TypeScript. Конкретный фреймворк (Express, Fastify, NestJS) — на усмотрение команды. Рекомендуется NestJS для структурированной модульной архитектуры, что упростит добавление ролей и провайдеров аутентификации в будущем.

**База данных:** PostgreSQL. Для многоролевой модели и будущих групп/соревнований реляционная БД подходит лучше документной.

**ORM:** Prisma (типобезопасность, удобные миграции).

**Требования к архитектуре:**

- Модуль аутентификации с абстракцией провайдера (email сейчас, OAuth позже). Для VK ID в экосистеме NestJS существует готовый модуль `nestjs-vkid`, поддерживающий OAuth 2.0 с PKCE ; для Express — стратегия `passport-vk-id` . Госуслуги (ЕСИА) требуют регистрации ИС на технологическом портале и работы с сертификатами — это отдельный этап интеграции .
- Модель данных, допускающая группы и соревнования: сущности `User`, `Group`, `GroupMember`, `Competition`, `CompetitionEntry` (или аналогичные). Даже если на первом релизе они не используются в UI, схемы должны быть заложены.
- API для синхронизации статистики (на будущее): приём записей о решённых кроссвордах, отдача агрегированной статистики.

### 6.4. Хранение статистики

**Клиент:** IndexedDB. Записи о каждом кроссворде: `{ userId?, crosswordId, timeSpent, mistakes, operations, difficulty, completedAt }`.

**Сервер (при включении синхронизации):** PostgreSQL. Таблица `game_results` с привязкой к `user_id`.

### 6.5. Деплой и инфраструктура

Бэкенд разворачивается на российском VPS (например, `rdp-onedash.ru` из черновика). Требования: HTTPS, автоматические бэкапы БД, минимальная конфигурация для первого релиза (один сервер приложения + PostgreSQL).


## 7. Требования к модерации RuStore

### 7.1. Возрастная маркировка

Указать возрастную категорию, соответствующую содержанию (обучающая игра без спорного контента). Маркировка должна быть корректной — модерация вправе скорректировать её при несоответствии .

### 7.2. Политика конфиденциальности

Если приложение собирает персональные данные (email при регистрации), политика конфиденциальности на русском языке должна быть доступна как в карточке RuStore, так и внутри приложения . При регистрации аккаунта необходимо предусмотреть возможность его удаления .

### 7.3. Качество приложения

Приложение должно стабильно запускаться на поддерживаемых версиях Android, не содержать ошибок вёрстки, выполнять заявленные функции . Тестирование на нескольких устройствах/версиях Android обязательно до подачи.

### 7.4. Карточка приложения

Название, иконка, скриншоты и описание должны соответствовать фактическому функционалу. Иконка в карточке и в установленном приложении должны совпадать (допустимы незначительные отличия фона/метки) . Скриншоты — не менее трёх на тип устройства, показывающие реальный интерфейс .


## 8. Этапность реализации

### Этап 1 (первый релиз)

- Фронтенд: PWA с кроссвордами базового и продвинутого уровня, настройками сложности, маскотом, локальной статистикой.
- Бэкенд: аутентификация по email, API для сохранения/чтения статистики (минимально необходимое).
- Упаковка в Android-сборку, прохождение модерации RuStore.

### Этап 2 (развитие)

- Синхронизация статистики между устройствами.
- Роли `родитель`/`организатор`, группы, соревнования.
- OAuth-провайдеры: VK ID → MAX → Госуслуги (по мере готовности интеграций).
- Голосовое сопровождение подсказок котика.

### Этап 3 (опционально)

- Экспорт статистики в GitHub (для продвинутых пользователей или отладки).
- Расширение контента: новые типы кроссвордов, адаптивная генерация под прогресс ребёнка.


## 9. Критерии приёмки

1. Игра запускается и полностью функциональна в браузере на десктопе.
2. Игра запускается и полностью функциональна как установленное Android-приложение **без интернета**.
3. Кроссворды генерируются корректно для всех заявленных диапазонов чисел и комбинаций операций.
4. Настройки сложности (диапазон, операции, отображение знаков) применяются к генерируемым кроссвордам.
5. Маскот присутствует, реагирует на правильные и неправильные ответы в соответствии с ТЗ.
6. Статистика сохраняется локально и переживает перезапуск приложения.
7. Аутентификация по email работает; архитектура допускает добавление OAuth-провайдеров без переработки ядра.
8. Схема данных и API допускают добавление групп и соревнований без миграции, ломающей существующие данные.
9. Приложение соответствует требованиям модерации RuStore (политика конфиденциальности, удаление аккаунта, качество сборки, карточка).
10. Монорепозиторий настроен: общие типы и конфигурация доступны фронтенду и бэкенду.


Настоящее ТЗ фиксирует требования к первому релизу и архитектурные заделы на будущее. Детали реализации (выбор фреймворка бэкенда, конкретная структура монорепозитория, дизайн кроссвордов) определяются командой разработки в рамках установленных требований.
